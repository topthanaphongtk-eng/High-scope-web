# Database — schema reference

Two equivalent schemas live here:

| File | Engine | Purpose |
|---|---|---|
| `schema_sqlite.sql` | SQLite | What the desktop app builds at runtime (single-file DB, fast local writes). |
| `schema_mssql.sql`  | MS SQL Server | Same shape adapted for SQL Server — for the team's central DB / web monitor. |

Both are kept **in sync by design** — adapter changes (Python's `MeasurementDB`) write the same fields under the same names; the only differences are dialect-level (data types, identity vs autoincrement, index syntax).

---

## Tables

### `lot_sessions` — one row per Confirm & Save action

| Column | Type (MSSQL) | Type (SQLite) | Notes |
|---|---|---|---|
| `session_id`     | `UNIQUEIDENTIFIER` PK | `TEXT` PK | UUID generated by the desktop client |
| `confirmed_at`   | `DATETIME2(3)` | `TEXT` (ISO 8601) | When the operator clicked Confirm |
| `lot_id`         | `NVARCHAR(64)` | `TEXT` | LOT ID typed/scanned at sign-in |
| `bonding_number` | `NVARCHAR(64)` | `TEXT` | From MES `LotDetail.Bonding_Running` |
| `lot_location`   | `NVARCHAR(64)` | `TEXT` | From MES `LotDetail.LotLocation` (machine / station) |
| `mpc`, `package`, `qs` | `NVARCHAR(64)` | `TEXT` | Lot context fields from MES |
| `operator_badge` | `NVARCHAR(32)` | `TEXT` | e.g. `B19277` |
| `hostname`       | `NVARCHAR(128)` | `TEXT` | Machine that wrote the row |
| `app_version`    | `NVARCHAR(32)` | `TEXT` | Desktop app version |
| `n_locations`    | `INT` | `INTEGER` | Locations measured (1–4) |
| `n_pads`         | `INT` | `INTEGER` | Total pad detections in this session |
| `raw_lot_info`   | `NVARCHAR(MAX)` | `TEXT` | JSON dump of full MES `LotDetail` |

Indices:
- `(lot_id, confirmed_at DESC)`
- `(bonding_number, lot_location, confirmed_at DESC)`
- `(confirmed_at DESC)`

### `measurements` — one row per pad detected

Many-to-one to `lot_sessions` via `session_id`.

| Column | Type (MSSQL) | Type (SQLite) | Notes |
|---|---|---|---|
| `id`             | `BIGINT IDENTITY(1,1)` PK | `INTEGER PRIMARY KEY AUTOINCREMENT` | |
| `session_id`     | `UNIQUEIDENTIFIER` FK | `TEXT` | → `lot_sessions.session_id` |
| `confirmed_at`, `lot_id`, `bonding_number`, `lot_location`, `mpc`, `package`, `qs`, `operator_badge` | (denormalized) | (denormalized) | Copied from session for fast filtering |
| `location`       | `NVARCHAR(8)` | `TEXT` | `TL` / `TR` / `BL` / `BR` |
| `pad_index`      | `INT` | `INTEGER` | 1-based; >1 when multi-pad detection finds extras |
| `pad_w_um`, `pad_h_um` | `FLOAT` | `REAL` | Pad rotated-rect size (always µm) |
| `ball_d_um`      | `FLOAT` | `REAL` | Detected ball diameter (always µm) |
| `gap_min_um`, `gap_mean_um` | `FLOAT` | `REAL` | Pad-edge → ball-edge gap |
| `confidence`     | `NVARCHAR(16)` | `TEXT` | `high` / `medium` / `low` |
| `pixel_size_um`  | `FLOAT` | `REAL` | µm per pixel from OME-XML |
| `source_ball_path`, `source_pad_path` | `NVARCHAR(512)` | `TEXT` | Operator's drop targets |
| `stored_ball_path`, `stored_pad_path` | `NVARCHAR(512)` | `TEXT` | Final destination in the share folder |
| `extra_json`     | `NVARCHAR(MAX)` | `TEXT` | Full `PadMeasurement.to_dict()` — forward-compat (polygon, gap per side, …) |

Indices:
- `(bonding_number, lot_location, confirmed_at DESC)`  ← trend queries
- `(lot_id)`  ← LOT detail page
- `(confirmed_at DESC)`  ← dashboard recent-list
- `(session_id)`  ← join back to session

### View `v_measurements_full`

Joins both tables. Web monitor uses this for one-shot reads:
```sql
SELECT * FROM v_measurements_full
WHERE bonding_number = ?
  AND lot_location   = ?
  AND confirmed_at >= ?
ORDER BY confirmed_at DESC;
```

### View `v_lot_summary` (MSSQL only — bonus)

One row per session with avg / min / max ball d + gap min across the 4 locations. Power BI / Excel reports hit this directly.

## Storing values: convention

* All linear dimensions are stored as **µm** (column suffix `_um`). Display unit (mil) is a presentation concern handled by the desktop and web layers.
* Timestamps are **ISO 8601 with timezone offset** in SQLite, native `DATETIME2` in SQL Server.
* JSON columns store the entire upstream record verbatim — schema evolution doesn't break old data; new fields appear in `extra_json` first.

## Bringing data over

The desktop app currently writes to SQLite. To seed SQL Server:

1. **Run the schema:** `sqlcmd -S server -d HighScope -i schema_mssql.sql`
2. **Export current SQLite data:** `python tools/export_to_csv.py`
3. **Import the two CSVs** with SSMS Import Wizard, BULK INSERT, or `bcp`:
   ```sql
   BULK INSERT dbo.lot_sessions
       FROM 'C:\path\to\lot_sessions.csv'
       WITH (FIRSTROW=2, FIELDTERMINATOR=',', CODEPAGE='65001', FORMAT='CSV');
   BULK INSERT dbo.measurements
       FROM 'C:\path\to\measurements.csv'
       WITH (FIRSTROW=2, FIELDTERMINATOR=',', CODEPAGE='65001', FORMAT='CSV');
   ```

Encoding: CSVs are UTF-8 with BOM, NULLs are empty cells, datetimes ISO 8601.
