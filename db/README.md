# Database — schema reference

> 🟢 **เพิ่งติดตั้งครั้งแรก / ไม่ถนัด software?** อ่าน [**คู่มือติดตั้งฉบับเริ่มจากศูนย์ (ภาษาไทย)**](SETUP-GUIDE-TH.md) — ทำตามทีละขั้นด้วย pgAdmin ได้เลย
>
> ไฟล์นี้เป็น **เอกสารอ้างอิงเชิงเทคนิค** (โครงสร้างตาราง + คำสั่ง command line)

The desktop stations and the Next.js web monitor share one **central PostgreSQL**
database. The schema lives in [`schema_postgres.sql`](schema_postgres.sql) —
neither the desktop app nor the web app creates tables at runtime; they only
read/write existing ones.

The schema covers **fused image captures only** — there is no measurement /
analysis data. Each Confirm event in the desktop app produces 1 row in
`captures` plus 1–3 rows in `capture_files` depending on the chosen mode.

---

## Tables

### `captures` — one row per Confirm & Save action

| Column | Type | Notes |
|---|---|---|
| `capture_id`     | `UUID` PK | UUID generated by the desktop client |
| `confirmed_at`   | `TIMESTAMP(3)` | When the operator clicked Confirm (local time) |
| `lot_id`         | `VARCHAR(64)` | LOT ID typed/scanned at sign-in |
| `bonding_number` | `VARCHAR(64)` | From MES `LotDetail.Bonding_Running` |
| `lot_location`   | `VARCHAR(64)` | From MES `LotDetail.LotLocation` (machine / station) |
| `mpc`, `package`, `qs` | `VARCHAR(64)` | Lot context fields from MES |
| `operator_badge` | `VARCHAR(32)` | e.g. `B19277` |
| `hostname`       | `VARCHAR(128)` | Machine that wrote the row |
| `app_version`    | `VARCHAR(32)` | Desktop app version |
| `mode`           | `VARCHAR(16)` | `mode1` (single fuse) or `mode2` (Ball+Pad+Weld) |
| `raw_lot_info`   | `JSONB` | Full MES `LotDetail` as JSON |

Indexes:
- `(lot_id, confirmed_at DESC)`
- `(bonding_number, lot_location, confirmed_at DESC)`
- `(confirmed_at DESC)`

### `capture_files` — one row per fused image saved

Many-to-one to `captures` via `capture_id`. Mode 1 has 1 file row, Mode 2 has 3 (Ball / Pad / Weld).

| Column | Type | Notes |
|---|---|---|
| `id`             | `BIGINT GENERATED ALWAYS AS IDENTITY` PK | |
| `capture_id`     | `UUID` FK | → `captures.capture_id` |
| `slot`           | `VARCHAR(32)` | `image` / `Ball` / `Pad` / `Weld` |
| `fused_path`     | `VARCHAR(512)` | Full path to fused TIFF in share folder |
| `fused_name`     | `VARCHAR(256)` | Filename only |
| `size_bytes`     | `BIGINT` | File size |
| `sha256`         | `VARCHAR(64)` | Hex digest, NULL if SHA disabled |

Index:
- `(capture_id)` — for fast lookup of a capture's files

## Setting up PostgreSQL

Run on the database host (e.g. `MTH-dk-b12416`).

### 1. Create the role + database

As a superuser (`psql -U postgres`):

```sql
CREATE ROLE highscope WITH LOGIN PASSWORD 'choose-a-password';
CREATE DATABASE highscope OWNER highscope;
```

### 2. Apply the schema

```bash
psql -h MTH-dk-b12416 -U highscope -d highscope -f db/schema_postgres.sql
```

Verify:

```bash
psql -h MTH-dk-b12416 -U highscope -d highscope -c "\dt"
# → captures, capture_files
```

### 3. Allow other machines to connect

The web monitor (and every station) connects across the network, so the
server must accept remote connections:

- **`postgresql.conf`** → `listen_addresses = '*'`
- **`pg_hba.conf`** → allow the plant subnet, e.g.
  ```
  host  highscope  highscope  10.50.0.0/16  scram-sha-256
  ```
- Restart the PostgreSQL service.
- Open inbound **TCP 5432** in the Windows firewall:
  ```bat
  netsh advfirewall firewall add rule name="PostgreSQL" dir=in action=allow protocol=TCP localport=5432
  ```

### 4. Point the apps at it

- **Desktop:** `config/settings.yaml` → `postgres.*` (or via the in-app Settings dialog).
- **Web:** `web/.env.local` → `PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD/PGSSLMODE`.

Set the password from step 1 in those (gitignored) files.

## File naming convention

Fused TIFFs are written to:
```
{shared_root}/{YYYY}/{MM}/{lot_id}/<filename>.tif
```
plus a sidecar `.json` with metadata (operator, OME-XML, etc.).

The `<filename>` follows:
- **Mode 1** (slot = `image`): `{LOT}_{Badge}_{LotLocation}_{TS}_{Host}.tif`
- **Mode 2**: `{LOT}_{Badge}_{LotLocation}_{Slot}_{TS}_{Host}.tif`

The desktop app also mirrors a per-capture record JSON to `{lot_dir}/_records/{capture_id}.json` so a web crawler can scan the share folder without touching the DB.

## Seeding from per-station SQLite (one-time migration)

Stations that ran the older SQLite-backed build can be migrated into the central PostgreSQL:

1. **Apply the schema** (step 2 above).
2. **Export each station's SQLite data:** `python tools/export_to_csv.py --db <station_db_path> --out ./db/exports/<station>`
3. **Import the CSVs** with `\copy` from `psql`:
   ```sql
   \copy captures      FROM 'captures.csv'      WITH (FORMAT csv, HEADER true, NULL '');
   \copy capture_files (capture_id, slot, fused_path, fused_name, size_bytes, sha256) \
        FROM 'capture_files.csv' WITH (FORMAT csv, HEADER true, NULL '');
   ```
   (skip the `id` column for `capture_files` — it is generated by the identity sequence.)

CSVs are UTF-8 with BOM, NULLs as empty cells, datetimes ISO 8601 — column order matches `schema_postgres.sql`.
