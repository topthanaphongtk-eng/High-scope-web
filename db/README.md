# Database — schema reference

The desktop stations and the Next.js web monitor share one **central SQL Server** database. The schema is owned by the DBA and lives in [`schema_mssql.sql`](schema_mssql.sql) — neither the desktop app nor the web app creates tables at runtime; they only read/write existing ones.

The schema covers **fused image captures only** — there is no measurement / analysis data. Each Confirm event in the desktop app produces 1 row in `captures` plus 1–3 rows in `capture_files` depending on the chosen mode.

---

## Tables

### `dbo.captures` — one row per Confirm & Save action

| Column | Type | Notes |
|---|---|---|
| `capture_id`     | `UNIQUEIDENTIFIER` PK | UUID generated by the desktop client |
| `confirmed_at`   | `DATETIME2(3)` | When the operator clicked Confirm |
| `lot_id`         | `NVARCHAR(64)` | LOT ID typed/scanned at sign-in |
| `bonding_number` | `NVARCHAR(64)` | From MES `LotDetail.Bonding_Running` |
| `lot_location`   | `NVARCHAR(64)` | From MES `LotDetail.LotLocation` (machine / station) |
| `mpc`, `package`, `qs` | `NVARCHAR(64)` | Lot context fields from MES |
| `operator_badge` | `NVARCHAR(32)` | e.g. `B19277` |
| `hostname`       | `NVARCHAR(128)` | Machine that wrote the row |
| `app_version`    | `NVARCHAR(32)` | Desktop app version |
| `mode`           | `NVARCHAR(16)` | `mode1` (single fuse) or `mode2` (Ball+Pad+Weld) |
| `raw_lot_info`   | `NVARCHAR(MAX)` | JSON dump of full MES `LotDetail` |

Indices:
- `(lot_id, confirmed_at DESC)`
- `(bonding_number, lot_location, confirmed_at DESC)`
- `(confirmed_at DESC)`

### `dbo.capture_files` — one row per fused image saved

Many-to-one to `captures` via `capture_id`. Mode 1 has 1 file row, Mode 2 has 3 (Ball / Pad / Weld).

| Column | Type | Notes |
|---|---|---|
| `id`             | `BIGINT IDENTITY(1,1)` PK | |
| `capture_id`     | `UNIQUEIDENTIFIER` FK | → `captures.capture_id` |
| `slot`           | `NVARCHAR(32)` | `image` / `Ball` / `Pad` / `Weld` |
| `fused_path`     | `NVARCHAR(512)` | Full path to fused TIFF in share folder |
| `fused_name`     | `NVARCHAR(256)` | Filename only |
| `size_bytes`     | `BIGINT` | File size |
| `sha256`         | `NVARCHAR(64)` | Hex digest, NULL if SHA disabled |

Indices:
- `(capture_id)` — for fast lookup of a capture's files

---

## File naming convention

Fused TIFFs are written to:
```
{shared_root}/{YYYY}/{MM}/{lot_id}/<filename>.tif
```
plus a sidecar `.json` with metadata (operator, OME-XML, etc.).

The `<filename>` follows:
- **Mode 1** (slot = `image`): `{LOT}_{Badge}_{LotLocation}_{TS}_{Host}.tif`
- **Mode 2**: `{LOT}_{Badge}_{LotLocation}_{Slot}_{TS}_{Host}.tif`

The desktop app also mirrors a per-capture record JSON to `{lot_dir}/_records/{capture_id}.json` so a web crawler can scan the share folder without touching the DB.

## Seeding from per-station SQLite (one-time migration)

Stations that ran the older SQLite-backed build can be migrated into the central SQL Server:

1. **Run the schema:** `sqlcmd -S server -d HighScopeCapture -i schema_mssql.sql`
2. **Export each station's SQLite data:** `python tools/export_to_csv.py --db <station_db_path> --out ./db/exports/<station>`
3. **Import the CSVs** via SSMS Import Wizard, BULK INSERT, or `bcp`:
   ```sql
   BULK INSERT dbo.captures
       FROM 'C:\path\to\captures.csv'
       WITH (FIRSTROW=2, FIELDTERMINATOR=',', CODEPAGE='65001', FORMAT='CSV');
   BULK INSERT dbo.capture_files
       FROM 'C:\path\to\capture_files.csv'
       WITH (FIRSTROW=2, FIELDTERMINATOR=',', CODEPAGE='65001', FORMAT='CSV');
   ```

CSVs are UTF-8 with BOM, NULLs as empty cells, datetimes ISO 8601 — column order matches `schema_mssql.sql`.
